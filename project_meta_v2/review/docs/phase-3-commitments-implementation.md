# Revoke 2.0 Phase 3 Commitments Implementation Review

Review date: 2026-09-04

Phase 3 replaces the user-facing Regimes management surface with a Commitment-oriented management, creation, detail, and edit experience. It deliberately retains the current schedule/taper persistence and native enforcement contracts.

## Change Summary

### Source files created

- `lib/features/commitments/commitment_presentation.dart`: explicit adapter from `ScheduleModel` and optional `TaperPlanModel` to `CommitmentViewModel`.
- `lib/features/commitments/commitments_screen.dart`: active, upcoming, paused, and attention-needed Commitment management list.
- `lib/features/commitments/create_commitment_screen.dart`: behavioral Reduce/Protect creation and editing journey, app selection, configuration, review, and activation.
- `lib/features/commitments/commitment_detail_screen.dart`: current state, plan, apps, edit, supported pause/resume, and end actions.
- `test/features/commitments/commitment_presentation_test.dart`: adapter mapping coverage.
- `test/features/commitments/create_commitment_screen_test.dart`: behavioral intent and legacy terminology boundary coverage.

### Source files modified

- `lib/core/app_router.dart`: `/commitments` now uses `CommitmentsScreen`; Commitment new/detail/edit routes were added; legacy `/regime/*` routes remain.
- `lib/features/today/today_screen.dart`: Today empty-state creation action now opens `/commitment/new`.
- `lib/core/models/taper_plan_model.dart`: optional persisted plan name, with a legacy-safe default.
- `lib/core/services/taper_plan_service.dart`: materialized schedules use the plan name; ended Reduce plans are archived locally and their materialized schedule is removed.

## Commitment Mapping

| User-facing concept | Current implementation |
|---|---|
| Protect daily limit | `ScheduleType.usageLimit`, native payload type `1`, `durationLimit`, selected days |
| Protect time period | `ScheduleType.timeBlock`, native payload type `0`, `ScheduleBlock` values, selected days |
| Reduce | `TaperPlanModel` plus materialized `ScheduleType.usageLimit` schedule, native payload type `1` |
| Unsupported Launch Count | Never produced by `CreateCommitmentScreen`; ambiguous existing records map conservatively to Protect with `Needs attention` |

## Domain Compatibility Boundary

`CommitmentViewModel` is a presentation/domain layer for the mobile UI. It owns user-facing type, status, summary, transition text, taper metadata, and source IDs. It does not replace `ScheduleModel` or duplicate `ScheduleBlockValidator` business rules.

The boundary is:

```text
Commitment UI
    -> CommitmentPresentationAdapter
    -> ScheduleModel / TaperPlanModel
    -> ScheduleService / TaperPlanService
    -> RegimeService + native sync
    -> existing Android enforcement
```

The backend still stores schedule documents under `users/{uid}/regimes`. No native/server Commitment document or immutable activation lease was introduced.

## Creation Flow

### Reduce

1. User chooses Reduce.
2. User searches and selects installed apps.
3. Revoke checks Usage Access and reads the existing per-package weekly Usage Insights bridge for a measured daily baseline.
4. User enters a daily target and chooses 2, 4, 6, or 8 weeks.
5. The review shows the actual linear taper values generated by `TaperPlanModel.dailyLimits`.
6. Activation calls `TaperPlanService.savePlanLocalFirst`, which writes the plan, materializes the current Usage Limit schedule, queues cloud sync, and triggers native synchronization through `ScheduleService`.

If a baseline cannot be measured, the flow does not substitute a default. Activation remains blocked and the user is directed to Usage Access.

### Protect

1. User chooses Protect.
2. User searches and selects installed apps.
3. User chooses Daily limit or Protected period.
4. Daily limit accepts minutes and selected days. Protected period accepts start/end times and selected days and uses `ScheduleBlockValidator`.
5. Review shows the human-readable boundary and app selection.
6. Activation calls `ScheduleService.saveSchedule` with the existing ID when editing or a new UUID when creating.

The flow does not expose schedule type enums or Launch Count. It does not add Credit backing, Premium, or override policy UX.

## Persistence

| Operation | Local | Firestore | Native |
|---|---|---|---|
| Protect create/edit | `ScheduleService` writes user-scoped SharedPreferences schedule cache | `ScheduleService` queues `RegimeService.saveRegime` to `users/{uid}/regimes/{scheduleId}` | `ScheduleService.syncWithNative` sends active schedule JSON |
| Protect pause/resume | `ScheduleService.toggleSchedule` updates the same schedule ID | Best-effort queued upsert | Active schedule list is re-sent |
| Protect end | `ScheduleService.deleteSchedule` removes the schedule locally and queues deletion | Best-effort delete | Active schedule list is re-sent |
| Reduce create/edit | `TaperPlanService.savePlanLocalFirst` writes user-scoped SharedPreferences plan cache and materializes a schedule | `users/{uid}/taperPlans/{planId}` plus schedule sync | Materialized type 1 schedule is sent through `ScheduleService` |
| Reduce end | `endPlanLocalFirst` archives the plan and deletes its materialized schedule | Archived plan is queued/upserted | Deleted materialized schedule is re-sent as absent |

Creation and editing preserve schedule IDs. `ScheduleService` remains local-first and Firestore/native work remains best-effort in the background.

## Native Enforcement Verification

The implementation was traced against `ScheduleService.syncWithNative`, `ScheduleModel.toJson`, and Android `MainActivity` schedule handling:

- Protect daily limits serialize `ScheduleType.usageLimit.index`, which is native type `1`.
- Protect periods serialize `ScheduleType.timeBlock.index`, which is native type `0`.
- Reduce materializes a `ScheduleType.usageLimit` schedule, which is native type `1`.
- The new creation flow has no Launch Count branch and cannot produce type `2` records.
- Existing Accessibility, UsageStats, overlay, alarm, watchdog, and temporary-unlock code was not changed.

## Terminology Migration

New user-facing surfaces use Commitment, Reduce, Protect, daily limit, protected period, target, allowance, plan, and active/paused/upcoming status language. Internal `ScheduleModel`, `ScheduleService`, `RegimeService`, `/regime/*` routes, Firestore `regimes`, and the retained `RegimesScreen` remain for compatibility and are not ordinary v2 creation vocabulary.

- Credit backing, purchase, Premium, and ledger settlement.

- Full taper remote hydration and schedule revision/conflict protocol.
- Multi-window progressive disclosure beyond the retained first block in the new default flow.
- Migration or removal of legacy `RegimesScreen`, `CreateScheduleScreen`, and old Home management widgets after reference proof.
- Completion history and trustworthy v2 outcome/adherence semantics.

## Implementation boundary conclusion

The user-facing Commitment model is implemented for the retained mobile schedule infrastructure. This is not a claim that the complete v2 Commitment backend exists. The smallest honest description is: v2 Commitment presentation and workflows over legacy schedule persistence and native enforcement.
